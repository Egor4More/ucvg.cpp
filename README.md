**UCVG** enables dynamic steering of LLM responses using “control vectors” (CVs). It ships three things: 
a new executable, `llama-ucvg`, which generates control vectors and saves them to a `.gguf` file; 
a modified `llama-server`, which applies those vectors with per-request-adjustable magnitudes; 
and 11 [pre-generated control vectors](tools/ucvg/examples/pregenerated-vectors/) for each of 10 common models.

## Quick start

> [!NOTE] 
> UCVG is prebuilt for, and runs on, any hardware that the original `llama.cpp` supports.

- Experiment with pre-generated control vectors quickly on the original llama.cpp (see below).
- Download a pre-built binary for your platform from the [releases page](https://github.com/Egor4More/ucvg.cpp/releases) or [build](docs/build.md) from source.
- Generate a custom control vector with `llama-ucvg` (see below), or use one of the bundled [example vectors](tools/ucvg/examples/pregenerated-vectors/).
- Steer with different magnitudes on a per-request basis with the modified `llama-server` (see API below), 
  or run the [Python demo](tools/ucvg/examples/ucvg_steer.py).



## Testing pre-generated CVs on the original llama.cpp

You can see how control vectors affect an LLM on the original [llama.cpp](https://github.com/ggml-org/llama.cpp) release without installing UCVG.
To do this, download one of the [bundled CVs](tools/ucvg/examples/pregenerated-vectors/) and run `llama-server` or `llama-cli` with one or multiple `--control-vector-scaled` flags with the path and vector strength in one string, separated by a colon. 
Refer to `summary.txt` at `tools/ucvg/pregenerated/<model-name>` to see the recommended usage range of each vector for the given model.

In unmodified llama.cpp, vector strengths are set at server startup and are therefore applied to all requests.
The only way to change a vector’s strength is to restart the server.

```shell
~/llama-unmodified/llama-cli \
  -m ~/models/gemma4.gguf \
  -c 8192 -ctk q8_0 -ctv q8_0 \
  --repeat-penalty 1.1 --reasoning off \
  --control-vector-scaled ~/vectors/neuroticism.gguf:0.04 \
  --control-vector-scaled ~/vectors/verbosity.gguf:-0.03
```

<br>

> **Windows note:** Global paths will not work for `--control-vector-scaled` because they contain a colon (`C:/`) and will trip up llama.cpp’s parser. 
> Use relative paths instead.  
> Bad:  `--control-vector-scaled "C:\vectors\gemma\verbosity.gguf:0.05"`  
> Good: `--control-vector-scaled ".\vectors\gemma\verbosity.gguf:0.05"`

## Generating control vectors (`llama-ucvg`)

Running `llama-ucvg` with the required flags will load the specified model into VRAM/memory, use the LLM to generate a small dataset, 
which is used to read activations across a set of prompts and produce a `.gguf` file containing the control vector. 
Afterward, it runs optional (`on` by default) autoscaling and evaluation.

A list of all flags with descriptions is available when running the executable with the `-h` flag, but here are some of the main ones (with examples):
- Path to the model, you are generating the vector for: `-m ~/models/gemma4.gguf`
- Output folder: `-o ~/vectors/`
- Trait name: `-t Happiness`
- Positive persona description: `-p "You are extremely happy"`
- Negative persona description (the polar opposite): `-n "You are extremely sad"`
- Evaluation on/off (default: on): `-e off`
  > Evaluation takes several times longer than the whole generation process and is not required to use the vector, 
  > but allows you to see how good the outcome is and approximate its usable range. 
  > To run just the range approximation (autoscaling) without the full evaluation, use `-e off -asc`

<br>

The examples above illustrate correct tool usage, but their persona descriptions were simplified. 
In practice, persona descriptions should mirror traditional system prompts and describe the character in the second person ("**You** are happy"). 
Ideally, each prompt should thoroughly describe a single trait from all relevant angles. 
Positive and negative prompts should be similar in phrasing and length, while describing polar opposites.
The corresponding personas should be mutually opposed such that their average approximates neutral human behavior.  
See [personas.md](tools\ucvg\examples\personas.md) for phrasing examples.


> [!NOTE]
> One vector works across different quantizations and fine-tunes of the same model, but a different model requires generating a separate vector.
> For example, vector A, generated on Gemma-4-26B-A4B at Q8_0 will work on the same model at 
> IQ4_NL and on an abliterated version of that model, but not on Gemma-4-31B or Qwen3.8-27B.

## Loading the vectors and using the modified server

The fork adds two optional, per-request JSON fields to `llama-server`'s completion endpoints along with two flags, passed at server startup. 
Load one or more control vectors with `--dynamic-cv-add <path>` (repeatable, order matters). 
Optionally set `--dynamic-cv-phase prefill|generation|both`. The default and the recommended mode is `generation`. `prefill` and `both` are experimental

- `additive_vector_coefficients` - an array of floats. Omit or set to 0 for no offset (no additive steering). 
  Applying positive offset will result in the model being constantly steered towards responding like the "positive persona" used when generating the vector. 
  Using negative offsets will steer in the opposite direction - the "negative persona"
- `multiplicative_vector_coefficients` - an array of `{"scale_positive": <float>, "scale_negative": <float>}` objects. 
  Omit or set to `{"scale_positive": 1, "scale_negative": 1}` for no offset. This parameter is experimental.
  An asymmetric *gain*: in contrast to a constant pull in one direction, this option amplifies the trait defined by the vector. 
  Using `scale_positive > 1` (or `scale_negative > 1`) makes the model express the positive (or negative) traits more strongly. 
  Values below 1 will dim the target trait. 
  > This parameter is experimental and is often unstable. Internal representations are non-linear, 
  > so linearly scaling them will likely not yield expected results 
  > (tends to show explosive behavior: either no effect at all, or an effect so strong that the model loses coherence)

The order of coefficients in a request must match the order in which the vectors were loaded.
In the example below, `happiness` was passed first and `verbosity` second. Thus, the curl request assigns an offset (additive steering) of 0.07 to happiness and -0.03 to verbosity.
Similarly, happiness will be scaled by 1.1 on the positive side and by 0.9 on the negative side (sadness). Verbosity by 0.75 on the positive side and 1.2 on the negative side.

Making a basic HTTP request with both vectors active:
```bash
curl http://localhost:8000/completion \
  -H 'Content-Type: application/json' \
  -d '{
    "prompt": "Tell me about your day.",
    "stream": false,
    "additive_vector_coefficients": [0.07, -0.03],
    "multiplicative_vector_coefficients": [ {"scale_positive": 1.1, "scale_negative": 0.9}, {"scale_positive": 0.75, "scale_negative": 1.2} ]
  }'
```

> [!TIP]
> For using stronger steering magnitudes in fields, where strong reasoning and output format are not as important (e.g. creative writing), 
> it is recommended to set higher repeat penalty (`--repeat-penalty 1.15` when starting the server or per-request) 
> to reduce the amount of looping that the models tend to produce at extreme steering magnitudes.

## Background - what ideas the tool is based on

Large language models are believed to encode certain concepts as specific directions in their
high-dimensional internal space. By reading the activations that flow from one layer of the model into
the next, we can approximate the direction the model uses to encode a particular concept.

The reverse operation is just as useful: if we take those same activations and offset them along a previously extracted
direction, we change the way the model responds. UCVG builds the extraction side (`llama-ucvg`) and
the application side (per-request steering in `llama-server`).

## Known limitations and issues

* **Out-of-distribution collapse.** Offsetting activations into regions the model never visited during
  training degrades response quality and can eventually collapse onto repeated tokens or noise. Accurately
  defining the target direction is therefore critical - a poor direction quickly steers the model out of
  distribution.
* **Lexical contamination.** Weaker models with worse understanding of complex concepts (e.g. human emotions) 
  at higher vector magnitudes tend to represent lexical symptoms of the trait, instead of the trait itself. 
  (e.g. high usage of "?!", capitalization and "omg" instead of representing actual anxiety)
* **Steering selectivity.** Encoding very specific instructions is difficult. 

<br>

* **Empirical scaling.** Today, vector quality is probed after generation is over, which is slow and unreliable. 
  An approach to automatically scale vectors so the stable range is inherently [-1; 1] is being searched for.
* **Parallel processing.** Setting `-np > 1` during vector application is experimental and introduces a risk of effects from one request leaking into another.
* **Multilingual datasets.** For minimizing lexical contamination, scenario generators are prompted to output situations in five different languages 
  but it seems like the used phrasing was too weak so some models keep outputting English-only stimuli.
* **Template mismatch.** Some models (e.g. GPT-OSS 20B and Muse-Glimmer) don't obey `reasoning:off`, which breaks the evaluation stage. 
* **Poorly readable evaluation**. The output of the evaluator (`eval_report.json`) is strictly formatted as a JSON, which makes readability worse.
